# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WeintCompanion is the official desktop companion app for the World of Warcraft addon **WeintCodex**. It's a PySide6 (Qt6) desktop application that installs/updates the addon, manages backups, and bridges data between the in-game addon and the **WeintCodex Bot** (Discord bot) via a small HTTP backend. Together these three repos form one ecosystem:

- **WeintCodex** – the WoW addon (Lua)
- **WeintCompanion** – this repo, the desktop app (Python/Qt)
- **WeintCodex Bot** – the Discord bot / backend

UI text, comments, and log messages are in German; code identifiers are in English.

## Commands

```bash
pip install -r requirements.txt   # install dependencies
python app.py                     # run the app
```

Tests live in `tests/` and run with pytest (`pip install -r requirements-dev.txt && python -m pytest tests/ -q`). They cover the framework-agnostic parts — config, installer, Lua/sync parsing, the analyzer and its academy evaluation, the replay reconstruction, and the navigation registry — plus `RaidDataService`'s live/archive/replay state machine and the live-update wiring in `tests/test_live_updates.py` (the update watch, the schedule sync's adaptive interval and change reporting, and the one `state_changed` the sync cycle makes of it — the last of those calls the real `_run_sync_worker()` on a `SimpleNamespace` rather than building a `CompanionManager`), both of which need PySide6 and httpx and `importorskip` themselves away when they are missing.

Five files **do** build widgets, all of them `importorskip("PySide6")` and all of them running under `QT_QPA_PLATFORM=offscreen`: `test_overlay_window.py`, `test_accent_follows.py`, `test_appearance_section.py`, `test_theme_connections.py` and `test_update_visibility.py`. They exist because the defects they cover are invisible to every non-visual test — a colour that silently stops following the accent, a control that is simply not there, a `lambda` that keeps a widget alive forever, and a segfault with no Python traceback. Running the suite needs the Qt system libraries (`libegl1`, `libgl1`, `libxkbcommon-x11-0`, `libxcb-cursor0` and friends); without them PySide6 fails to import and those files skip themselves rather than fail. There is no linter or formatter configured.

### Building distributables

```bash
./scripts/build_linux.sh          # PyInstaller build -> dist/WeintCompanion
./scripts/build_appimage.sh       # wraps the Linux build into an AppImage (requires linuxdeploy)
./scripts/build_windows.ps1       # PyInstaller + Inno Setup -> dist/WeintCompanion-Setup.exe
```

CI (`.github/workflows/build.yml`) builds Linux (AppImage) and Windows (Inno Setup installer) on every `v*` tag push and publishes a GitHub Release with both artifacts. `WeintCompanion.spec` is the PyInstaller spec (entry point `app.py`, bundles `assets/`, `resources/icons`, and the Linux updater script).

## Architecture

### Layering

- **`core/`** – all business logic, framework-agnostic where possible (Qt is used for `QObject`/`Signal` in a few places like `CompanionManager`, `RaidDataService` and `AppState`).
- **`gui/`** – PySide6 UI: `main_window.py` (frameless, own title bar), `navigation.py` (the page registry, see below), `pages/` (Overview, WeintTV, Academy, Archive, Characters, Preparation, Charakterzuordnung, Addon, Connections, Settings, Logs), `widgets/` (incl. `tv/`, `academy/`), `theme/` (see below), `layout/breakpoints.py`, `motion/pulse_clock.py`, `overlay/` (the small always-on-top window), `controllers/`, `dialogs/` (`whats_new_dialog.py` – the onboarding/changelog popup, and `setup_wizard.py` – the four-step first-run setup).
- **`analyzer/`** – the Raidlog Analyzer. **Contains no Qt import at all**, deliberately: it must stay testable without a running UI and extractable into its own package later. Holds the data models, the combat-log locator, the encounter/lesson reference data, the data providers, and the academy evaluation.
- **`addon/`** – reads and writes the WoW addon's Lua `SavedVariables` files (`finder.py` locates the WoW install, `reader.py` reads the addon's own version/state, `sync_reader.py` reads the outbound message queue, `inbox_writer.py`/`addon_inbox.py` write the inbound one, `addon_payloads.py` builds the WeintTV/Academy payloads).
- **`discord/`** – `sync_client.py`, a thin HTTP client for the material-sync bridge.

### `CompanionManager` is the app's central hub

`core/companion_manager.py` wires together nearly every subsystem (config, logger, GitHub updater, backup, installer, self-updater, launcher, sync manager, Discord status/auth/roster-sync) and is owned by the GUI layer. Its `full_refresh()` is the app's main "check everything" entry point: detect WoW install → detect addon → check GitHub for addon updates → check Discord bot status → check for Companion self-updates → run sync. `refresh_update_status()` is the lighter variant used by the manual "check for updates" button (skips Discord/sync).

Initialization pattern to preserve: `initialize()` schedules `_initialize_async` via `QTimer.singleShot` so the window renders before the background `InitThread` runs `full_refresh()`. Because that thread has no Qt event loop of its own, it can't reliably reach the main thread with `QTimer.singleShot(0, ...)` — it signals `_AutoSyncStarter.requested`, a cross-thread Qt signal, to invoke `start_auto_sync()` back on the main thread instead. Auto-sync itself runs on a recurring `QTimer` (`sync_interval` from config) that spawns a new `SyncThread` per tick, guarded by `_sync_busy` + a lock so overlapping syncs never run concurrently.

### Navigation: one registry, never raw indices

Pages live in a `QStackedWidget` whose index *is* the position in the sidebar rail. Both are built from a single source: `PageId` (an `IntEnum`) and `build_page_specs()` in `gui/navigation.py`. `MainWindow` iterates the specs to create the stack and hands the same list to `NavColumn(manager, specs)`, so rail and stack cannot drift apart. Adding a main area = one enum member + one `PageSpec`.

Never write a bare integer as a navigation target: `pageRequested.emit(PageId.ADDON)`, not `emit(1)`. `PageId` inherits from `int`, so it works unchanged with `Signal(int)` and `setCurrentIndex()`. `build_page_specs()` imports the page classes *inside the function body* — the pages import `PageId` themselves, so a module-level import would be circular.

Pages are built **on first entry**, not at startup. The stack is filled with one empty placeholder per spec so its index still *is* the `PageId`, and `MainWindow._ensure_page()` swaps the placeholder for the real page the first time it is needed — `insertWidget(index, …)` then `removeWidget(placeholder)`, in that order, or everything after it shifts. Building all ten up front cost about two seconds of a four-second start for pages the user mostly never opens; WeintTV and the Academy dominate it because they deliberately pre-create their list and table rows so later per-second redraws stay flicker-free (right decision, wrong moment). `_ensure_page()` is consequently the single place a page comes into existence: named attribute (`self.overview`, `self.settings`, …), scroll wrapper, and the duck-typed cross-page signals (`pageRequested`, `playerRequested`, `openSettingsSection`) are all wired there. Anything that reaches for a page directly — `open_settings_section()`, `open_academy_for()` — must go through it rather than through the attribute, which may not exist yet.

`MainWindow.change_page()` calls three duck-typed hooks on a page if present: `on_leave()` on the outgoing page, then `on_enter()` and `refresh()` on the incoming one. WeintTV and the Academy use `on_enter`/`on_leave` to subscribe to and release the raid data feed, so nothing polls while its page is hidden.

### The 2.0 theme: one token table, one manager

`gui/theme/tokens.py` is **the only place a colour, spacing, radius or type size exists** (the one exception is `wow_colors.py`, a domain table like those under `analyzer/data/`). It imports no Qt at all — same reason `analyzer/` doesn't: `tests/test_tokens.py` checks it without a running UI. `gui/theme/stylesheet.py` is therefore a function, `build_stylesheet(theme)`, not a constant.

`gui/theme/theme_manager.py`'s `ThemeManager` is a singleton reached through `theme()` and initialised once via `init_theme(config)`. It owns the three user choices — accent (three variants), density (`comfortable`/`compact`) and reduced motion — and announces each with its own signal (`accent_changed`, `density_changed`, `motion_changed`). All three are set in **Settings → Erscheinungsbild** (`gui/pages/settings_sections/appearance.py`) and, for the first run, in the setup wizard; the swatches they share live in `gui/widgets/appearance_picker.py`, and the German labels with them, so a fourth accent variant cannot appear in one place and be missing in the other. That page was for a while the biggest hole in 2.0: the manager could do all three, stored all three, but the only UI was the wizard, so whoever finished it once could never change the accent again. `ThemeManager.user_motion_reduced()` exists expressly for "what the switch in Settings has to show" — the switch was simply never built. The switch must show *that* and not `motion_reduced()`, which is the OR with the system setting: with the system forcing it, the switch would read "on" and clicking it would change nothing visible, i.e. look broken. A line underneath says when the system is the reason.

Six things follow from those signals, each of which was a real defect once:

- **A painted widget must read the accent in `paintEvent`, never in `__init__`.** A colour captured at construction survives an accent switch and the widget keeps the old one — silently, since nothing errors. The ring, sparkline, stars, bars and the nav indicator all re-read `theme()` while painting; that is what the accent walkthrough in the verification actually proves.
- **Reading in `paintEvent` is not enough if the value comes from `gui/theme/colors.py`.** That module is the documented transition table from the old `Colors.*` names to the tokens, and its values are **static** — frozen at amber when it is imported. `MeterBar` read `Colors.PRIMARY` inside its `paintEvent` and still never changed colour; `HeroButton` — the app's main button, in thirteen modules — built its stylesheet once in `__init__` from the same table. Both are fixed to `theme().accent_base()`/`accent_light()`, and `HeroButton` also takes its text colour from the variant's `onBase` instead of a hard `color:white`, because jade is lighter than amber. `tests/test_accent_follows.py` renders each accent-bearing widget under all three variants and compares the images; a widget that keeps its colour produces one image instead of three.
- **Connect to `accent_changed` in `__init__`, never inside the handler it triggers.** Connecting from the handler doubles the connection on every switch (measured 1, 2, 4, 8, 16). It never looks like a bug, only like the app getting slower.
- **Never connect a `lambda` to one of the three signals.** `theme()` is a singleton and lives as long as the process, so a `lambda _n: self.update()` hands it a hard reference to `self` and the widget is never freed again — nine widgets did this, among them `ToggleSwitch`, `ProgressRing`, `Sparkline` and `SegmentedControl`, i.e. the ones that occur by the dozen in lists and tables. If the C++ object *is* destroyed anyway because a parent goes away, the lambda then fires into it and Qt raises `RuntimeError: Internal C++ object already deleted` from inside a slot, where an exception is hard to trace. A **bound method** fixes both: PySide6 holds the receiver weakly and Qt drops the connection when it is destroyed. `QObject.receivers()` is no way to check this — PySide6 does not count it down even when the connection really is gone; `destroyed` is. The same trap one level in: `button.toggled.connect(lambda checked, b=button: …)` in `SegmentedControl` closed a cycle (control → button → connection → lambda → control) that the garbage collector cannot see, because the lambda sits in the C++ connection; the handler asks `sender()` instead. `tests/test_theme_connections.py` holds both halves — every such widget must be released after its last reference is dropped, and no `theme().…connect(` line may contain a `lambda`.
- **A `font-size` on the `QWidget` rule overrides every `setFont()` in the program.** That is why the `QWidget` rule in `build_stylesheet()` deliberately carries no font declaration and the base font is set once with `QApplication.setFont()` in `apply_stylesheet()`. Before that, every piece of text in the app was 14 px regardless of its role.
- **`QFont(family, size)` sets a *point* size.** `gui/theme/fonts.py` uses `setPixelSize()`; the token table is in pixels. `install_fonts()` registers the bundled Inter and JetBrains Mono (in `WeintCompanion.spec`'s `datas`) — Qt's fallback still supplies glyphs those two lack (`●`, `▶`, `★`, `—`), so those characters are safe in UI strings, but nothing else about the metrics is.

Qt's stylesheet engine knows no `transition`, no `@keyframes` and no `letter-spacing`; animation lives in `gui/theme/motion.py` (`duration()`, `curve()`, `is_reduced()`), the shared blink in `gui/motion/pulse_clock.py`, and letter spacing is set on the `QFont`. `gui/layout/breakpoints.py` is Qt-free too: `resolve(width, previous)` with 40 px of hysteresis, so a window dragged across a threshold doesn't flicker between two layouts.

**Not every motion token has a consumer, and that is worth knowing before you go looking for the bug.** `MOTION` in `gui/theme/motion.py` describes thirteen movements; eight are live (`page`, `bar`, `toast_in`, `toast_out`, `progress`, `nav`, `toggle`, `expand`, plus `pulse` through `gui/motion/pulse_clock.py`, whose period now *reads* `MOTION["pulse"]` instead of repeating the 1000 as its own constant). Four describe things the 2.0 UI does not have yet, and they are aspiration rather than defect: `number` (no value counts up anywhere — `should_animate_number()` and `suspend_value_animation()` are the guards written for it and have no callers yet), `skeleton` (`gui/widgets/skeleton.py` is complete and used by nobody; loading is currently said in words, e.g. "Lädt Berichte …" in the archive picker), `hover` (Qt's stylesheet engine has no `transition`, so `:hover` is instant everywhere and a 120 ms hover would have to be hand-animated per widget), and `drawer` (the flag `LayoutState.drawer` exists and is read — but only as a *breakpoint* for the Academy's rating grid; the sliding side panel it was named for does not exist). `expand` was the one that was genuinely missing rather than unbuilt: the Overview's system row jumped from 44 to 132 px, and that row is exactly where a background check announces itself, so the jump read as a glitch rather than as something arriving.

**Animations must be stopped and released, not just replaced.** A `QPropertyAnimation(…, self)` or `QVariantAnimation(self)` is a child of its widget: reassigning the attribute drops the Python reference but the C++ object stays. Reuse one animation per widget where the target is fixed (`BarRow._set_fraction`), or start with `DeleteWhenStopped` and clear the reference in the `finished` handler (`MainWindow._animate_page`, `NavColumn._apply_collapsed`) — and stop the previous one first, or two animations drive the same property at once. Measured before the fix: 199 objects on a single bar row after 200 relabels, one group per page change for the window's lifetime.

### WeintTV and WeintAcademy: one service, one snapshot

Both modules read the **same** `RaidSnapshot` (`analyzer/models.py`) — an immutable, complete picture of one moment (boss health, pull timer, deaths, battle-res, heroism, DPS/HPS rankings, tanks, cooldowns, consumables, mechanic errors, warnings). No widget ever sees a combat-log event, and no page computes a metric. That is what structurally prevents WeintTV and the Academy from growing two divergent evaluations.

Uptimes come in three lists, not two: `dot_uptimes`, `hot_uptimes` and `buff_uptimes` (effects on the player themselves — `UPTIME_BUFF`). The third exists because a tank's active mitigation is neither: filed under HoTs it would only ever be read for healers, and left out entirely it took the whole tank contribution with it. `uptimes_of(name, kind)` is the single accessor, `players[].buffs[]` the (optional) bridge field, and WeintTV shows it as its own card next to the DoT and HoT cards.

The one thing the snapshot carries *without* evaluating it is `events: tuple[CombatEvent, ...]` — phase changes, announced boss casts, adds. `CombatEvent.kind` is a free string on purpose: an unknown kind must land in WeintTV's event list unchanged rather than be dropped, so a new kind from the bot needs no Companion release. Everything the analyzer actually *reasons about* (deaths, resurrects, interrupts, dispels, mechanic issues) keeps its own typed field, because the Academy needs those separated — a dispel and a death train different areas. They are merged onto one time axis only in `WeintTvPage._event_rows()`, i.e. in the presentation, where order is all that matters. Putting anything into `events` that also has a typed home would double-count it. `analyzer/replay/models.TimelineEvent` is an alias of `CombatEvent`, not a second class: the timeline supplies exactly these and `snapshot_at()` hands them straight through, up to the current second.

`core/raid_data_service.py`'s `RaidDataService` is the single place that picks and polls a data source. Key points:
- Sources are registered in `PROVIDER_FACTORIES` keyed by the `raid_data_source` config value, alongside `SOURCE_LABELS`/`SOURCE_DESCRIPTIONS` for the picker in Settings → Module. A new source (live combat log, bot backend) is one entry plus a class implementing `analyzer/providers/base.py`'s `RaidDataProvider` — no change to the service or the pages. Factories are called with no arguments; anything a provider needs is wired in the factory (see `_create_warcraftlogs_provider`). An unknown key logs a warning and falls back to the mock, so the UI always stays usable.
- `attach()`/`detach()` are reference-counted; the `RaidDataThread` (a plain `threading.Thread`, matching the rest of the repo) runs only while at least one page is subscribed, on its own ~1s cadence — deliberately *not* on `CompanionManager`'s 5-second sync timer, which is for HTTP sync.
- Results reach the GUI through the `snapshotChanged = Signal(object)` cross-thread signal; the service is constructed in `CompanionManager.__init__` (main thread) so its thread affinity is right.
- It also owns the pull history (`PullSummary`), so the history view and any later analysis see the same completed pulls.

`analyzer/providers/mock.py` produces a fully deterministic 25-player pull from elapsed time — no randomness, so the same moment always yields the same snapshot. It is what makes WeintTV reviewable outside raid hours and is the proof that the UI really only reads snapshots. Its roster and schedules live in `mock_schedule.py`, which also *derives* every player's uptimes and cooldowns from their spec via `class_abilities` — the hand-written rows (which tell specific stories: Krallenwut leaves his Berserk unused, Feuerbrand drops his Immolate) always win, the derived ones fill the rest. Before that, only seventeen of the twenty-five had any uptime rows at all, and an Elemental Shaman or Windwalker looked exactly like a spec nobody had ever filled in. Derived rows deliberately carry the **German** name while the hand-written ones stay English: a real report arrives in whatever language uploaded it, so the simulation exercises both paths through `spec_reference`, and a broken match shows up immediately as a duplicated row.

The Academy adds `analyzer/academy/`: `evaluator.py` turns a snapshot into a `PlayerProfile` (star ratings for **six** areas — Rotation/Movement/Cooldowns/Mechaniken/Überleben/Leistung) and a `TrainingPlan`, using the `MECHANIC_*` category on each `MechanicIssue` to attribute errors to a trainable area. Ratings are **relative to the player's own role** — comparing a tank against the damage ranking would permanently score them one star, and for damage *taken* that matters even more (a tank always takes the most, which is the job), so Überleben rates the avoidable **share** against same-role peers, never the absolute sum. Relative alone isn't enough either: it rewards conformity (if every DPS makes the same mistake they all sit at the average and all score full marks) and it degenerates when someone is the only player of their role with data — they'd be compared against themselves. Überleben therefore takes the **stricter** of the relative and an absolute rating (`ABSOLUTE_AVOIDABLE_SHARE`). `core/academy_service.py` only handles character selection and persistence (`academy_progress.json` in `Paths.config()`, because completed lessons are user data, not cache).

Three rules the Academy lives by, each of which reverses an earlier mistake:

- **Rotation must not read the damage ranking.** That was the original implementation and it measured gear, not play. Rotation is now active time, APM and aura uptimes; the rank moved to its own area, `Leistung`, where it no longer overshadows the question "did I press my buttons right". *Which* uptimes count is role-dependent (`_uptime_parts`): DoTs for damage, HoTs for healers, and for tanks the **active mitigation** from `buff_uptimes` — a tank has neither DoTs nor HoTs, so Rotation used to fall back to active time alone, i.e. the one number that says least about a tank. Mitigation is rated there and *not* under Überleben, which asks about the outcome (avoidable damage, deaths); rating it twice would charge the same incident twice, exactly the mistake that once moved deaths out of Mechaniken.
- **No comparison group, no rating.** Being the only player of your role means the best of the group is yourself, the ratio is always 1.0 and the stars are always five — regardless of how the pull went. `Leistung`, the movement average and Überleben all require at least one other player of the same role with data, and otherwise answer "keine Daten". In a ten-man that regularly hits the only tank and the only healer, i.e. precisely the people a free top mark helps least.
- **`stars = 0` means "no data", not "bad".** Without that distinction a gap in the data source outranks every real weakness and hijacks the whole training plan. `PlayerProfile.rated`/`weakest` skip zero-star ratings, and `_combine()` drops parts that have no data instead of averaging them down.
- **Lesson results and the manual checkbox are never merged.** `LessonResult` is evidence from the log, `completed` is the player's own claim. Auto-ticking would assert something a single pull can't support; auto-unticking would destroy the player's own record.

The training plan verifies itself: a `Lesson` carries declarative `LessonCheck`s ("active_percent >= 95"), and **`analyzer/academy/checks.py` is the only place** mapping metric names to snapshot lookups. `tests/test_lesson_catalog.py` asserts every metric used in the catalog resolves there — a typo would otherwise be a permanently silent "keine Daten". Outcomes are three-valued (`passed`/`failed`/`unknown`) because many lessons aren't measurable in principle and many payloads omit blocks; a red cross for a missing field would simply be wrong.

The catalog is a package (`analyzer/academy/lessons/`): `generic.py`, `roles.py`, `classes/<class>.py`, `encounters.py`, merged by `registry.py`, which **raises on a duplicate `lesson_id`** at import — the id is the persistence key, so a duplicate would silently merge two lessons' progress. Selection order is encounter → spec → class-wide → role → generic. Catalog opt-out stores **exclusions, not inclusions**, so a newly shipped lesson is automatically active for everyone with no migration. All 34 MoP specs carry their own Rotation and Cooldown lessons, every class its utility lessons at the class-wide (`spec=""`) level, and every tank spec at least one `buff_uptime` check on its active mitigation; `tests/test_lesson_catalog.py` holds those three floors, because a spec with a single lesson silently degrades to generic advice from the second training plan onwards.

Two tables under `analyzer/data/` exist because **the catalog is written in one language and the data source answers in another**, and both failures were silent — indistinguishable in the UI from "the bot doesn't send this block":

- `specs.py` — all 34 specs with German name, English name and role. The catalog and the mock use the German spelling ("Vergeltung"), WarcraftLogs sends the English one ("Retribution"), so before this table no spec key ever matched in production and every player got role/generic lessons only. It also answers the second question the payload cannot: **the role follows from the spec**. Without it a missing `role` field was guessed from damage vs. healing, which can never yield "tank" — and a tank filed as a damage dealer is measured against the damage ranking. `warcraftlogs_payload.build_actor()` (and the replay's `_actor()`, so both paths produce the same identity) normalise through it; an unknown spec passes through unchanged, same rule as for class names.
- `player_abilities.py` — German ↔ English for the abilities the lesson checks name, used by `checks.py` when matching `subject` against an uptime or cooldown row. Additive by design: a missing entry costs a match, it never invents one. Separate from `avoidable.py`'s alias table, which maps *boss* abilities and carries a judgement. It no longer stands alone: `_all_names()` merges `class_abilities.translations()` into it, because that table carries both names for every ability it lists anyway and two hand-maintained translation lists would drift — silently, as always, into a lesson that says "keine Daten" forever.

- `class_abilities.py` — **what a spec would have to show in the first place**: all 34 specs with their DoTs, HoTs, self-buffs (for tanks the active mitigation) and cooldowns, each with spell IDs, English *and* German name, a target uptime or a cooldown duration, and a category. Seeded from the Raidlog-Analyzer's registries (`DOT_REGISTRY`, `HOT_REGISTRY`, `DPS_COOLDOWNS`, `ACTIVE_MITIGATION`, …) and completed for the specs it had no rows for. Three rules: an ability is recognised by **spell ID, English name or German name** — one of the three is enough, so a mis-remembered ID doesn't break an entry; anything talent- or glyph-dependent is `optional` and is therefore only ever *shown*, never *expected*; and the target uptime lives here rather than in the UI, so WeintTV and the Academy cannot measure the same effect against two yardsticks. German names are best-effort (there is no client to verify them against) — `aliases` exists precisely so a second spelling costs nothing. That best-effort status is not harmless on its own: a diff against the bot's own catalogues found **35 spell IDs carrying a different German name on each side** (Zerfleischen/Hauen, Aufstieg/Aszendenz, Seelenruhe/Gelassenheit …). Matched by name, each of those is a permanently unrecognised row — which looks exactly like an ability the player never used. The structural answer is on the wire, not in the table: the bot now sends `spell_id` on every ability row, and `match()` reads the ID first, so the two spellings may differ without costing a match. The table's German name then only decides what is *displayed*.

Two entries were not spelling but plain wrong, and both were the same kind of silent error — a real number under the wrong name: `31842` sat in **Avenging Wrath** (it is Divine Favor) and `123040` in **Shadowfiend** (it is Mindbender, 60 s cooldown instead of 180, so every Mindbender was measured against triple its recharge and scored "barely used"). `tests/test_class_abilities.py` now asserts no spell ID is claimed by two different abilities, and holds the eighteen DoTs from the user report as a floor — by ID, by German name, and by "belongs to at least one spec".

`analyzer/analysis/spec_reference.py` is what that table is for. `apply_spec_reference(snapshot)` runs at the end of `snapshot_from_payload()`, in the mock and in `snapshot_at()` — every path that produces a snapshot, so live, archive, replay and simulation cannot disagree — and it fixes three failures that all looked identical in the UI ("Keine Angaben zu …"): a report in the wrong language, an aura filed in the wrong one of the three lists, and an ability that simply wasn't reported. The line it must never cross is between **a finding and a data gap**: a missing ability is filled in with 0 % only when the source demonstrably delivers that kind of uptime for *someone* — a zero is a claim, and it may only stand where the source actually looked. When the source delivers nothing of that kind, nothing is claimed; instead `reference_hint()`/`cooldown_hint()` let WeintTV's empty card and the Academy's unrated area say what *would* be shown for this spec. The same restraint governs `possible` on cooldowns: only `CD_PERSONAL` gets an upper bound, because an unused Shield Wall is a fight that didn't need it, not a wasted use — and counting it would hit tanks and healers hardest, i.e. exactly the roles that own the most defensives. `_rate_cooldowns()` in the evaluator follows that same split.

Recognised rows are also **renamed to their German name**, including `raid_cooldowns`/`heal_cooldowns`, whose `CooldownState` rows describe the same abilities as a countdown: which language a report arrives in is an accident of who uploaded it, and "Rallying Cry" in one card next to "Sammelschrei" in the next is the same ability twice. `match()` takes a `prefer` argument because a few abilities are both an aura and a cooldown under one spell ID (Brewmaster's Guard, Windwalker's Tigereye Brew) — without it the lookup order would decide, and a reported cooldown row would come back with an aura's (absent) cooldown.

`analyzer/analysis/` sits between `data/` (reference knowledge) and `providers/` (ingestion) and holds the derivations both the payload mapper and the replay need: `ranking.py` (extracted so the two can't drift apart on shares and sorting), `movement.py` (the single map-units-to-metres constant), `damage.py` (bucketing damage taken, deriving mechanic issues, merging them with the bot's).

**Whether a hit was avoidable is a judgement, not a measurement**, so it lives in `analyzer/data/avoidable.py` and not in the bot: it must be identical for WeintTV and the Academy, it changes with difficulty and tactics, and it has to stay correctable without a bot deploy. The verdict is deliberately **three-valued** — an ability missing from the table is `unknown`, never `unavoidable`. Treating unknown as unavoidable would hand every boss without reference data a flawless survival rating. The table covers all fourteen Siege of Orgrimmar encounters plus Horridon (which the mock reproduces) — every fight is represented, but not every ability of every boss: only the ones where the verdict is unambiguous. A wrongly-avoidable rule accuses a player who did nothing wrong, which is worse than a gap. Below `MIN_CLASSIFIED_SHARE` the Academy declines to rate at all rather than grade the table's gaps. When the bot ships its own hand-written `mechanics[]` rows, `merge_mechanics()` lets **the bot win** per (player, ability) so the same incident isn't counted twice; an alias table bridges the bot's German texts to English ability names, and it is **derived from the rules' own labels** rather than hand-maintained — a second list would drift, and the symptom would be a double-counted error nobody recognises as one.

The second real source is **WarcraftLogs**, read through the bot rather than directly: the bot sees the Discord webhook the live-logging uploader posts, holds the WarcraftLogs API credentials, and serves the result at `/companion/warcraftlogs/live`. That split keeps credentials off 25 player machines and shares one API quota. Three files, deliberately separated so the analyzer stays dependency-free: `analyzer/providers/warcraftlogs_payload.py` is a pure response → `RaidSnapshot` mapper (no I/O, reads defensively — an incomplete response is never an error); `analyzer/providers/warcraftlogs.py` is the provider, which takes its fetch as an injected callable and runs its **own** 15-second fetch thread so `snapshot()` reads a cache and never blocks the service's 1-second poll; `core/warcraftlogs_client.py` is the HTTP half, wired to the provider in the factory. Unlike the combat log it lags by tens of seconds (the provider advances the pull clock locally between fetches and warns past 45s) but covers the whole raid without this machine logging. **All five bot endpoints now exist**, `/timeline` included (`services/warcraftlogs.py` and `services/warcraftlogs_timeline.py` in the bot repo). The deep-analysis fields the six Academy areas and the replay need are specified as **v2** in `docs/warcraftlogs-bridge.md`; a first round of them was implemented in the bot but arrived empty for two reasons worth remembering, because both are silent failures: WarcraftLogs localizes **ability names** (a German log says "Seelenruhe", so an English-name lookup matched nothing and every cooldown list stayed empty), and Buffs/Debuffs tables answer with `auras` rather than `entries` (so per-player DoT/HoT uptimes were always `{}`). The bot now matches abilities by spell ID with English *and* German names as independent fallbacks, and reads uptimes from raw events, where alone the caster is known. Every v2 field is optional and additive: a missing block degrades to "keine Daten" in the UI and to an unrated (zero-star) area in the Academy, never to a bad rating. `RaidSnapshot.has_analysis` is the single switch the UI uses for that, instead of null-checking each field: WeintTV hides the whole deep-analysis block behind it and the Academy explains its unrated areas with it. What it does *not* say is **why**, and the three answers ("no raid", "no pull running", "this source only sends sums") lead to completely different expectations — only the last one means "nothing you can do until the bot ships more". `gui/widgets/tv/analysis_gap.py` is the one place that decides which of the three it is, shared by both pages so they can never explain the same situation differently. It is under `gui/` but imports no Qt, so it stays testable without a running UI.

### Archive mode: reviewing a past report instead of the live feed

Both WeintTV and the Academy can also show a single, long-finished WarcraftLogs fight instead of the live feed — pick a report, pick a pull inside it. This is deliberately **not** called "Verlauf" in the UI (that name is already taken by WeintTV's own completed-pulls-this-session tab, backed by `PullSummary`/`history()`); the second, unrelated "past report" concept is called **"Archiv"** everywhere in code and UI to avoid the collision. It's also deliberately global on `RaidDataService`, not per-page state: the same "one snapshot" principle that keeps WeintTV and the Academy from diverging on the live feed applies here too, so switching to Archive on one page switches it on the other.

`RaidDataService` grows a `MODE_LIVE`/`MODE_ARCHIVE` mode plus an `ArchiveState` (reports/fights lists, loading/error flags per step, current selection), exposed via `archive_state()` and mutated through `enter_archive_mode()` → `select_archive_report()` → `select_archive_fight()` → `show_live()`, each step notifying `gui/widgets/tv/archive_picker.py` (shared by both pages) through the `archiveChanged` signal. Each step's HTTP call runs in its own short-lived thread (same pattern as `WarcraftLogsProvider`'s fetch thread) so a slow bot response never freezes the UI; a stale in-flight result (user already picked something else by the time it lands) is detected and dropped. Picking a fight publishes a normal `RaidSnapshot` via `_publish(snapshot, track=False)` — same function the live poll uses, `track=False` just means it doesn't pollute the session's `PullSummary` history, since it isn't a pull that's actually happening now. While pinned to an archived fight, the live poll thread keeps running in the background (harmless — it's either pure computation or reads from an existing cache) but its results are discarded rather than published, so switching back to Live is instant instead of waiting for the next poll tick.

`core/warcraftlogs_archive_client.py` is the HTTP half for three additional bot endpoints (report list, fight list per report, one fight by ID) — same auth/error shape as the live client. **Trash is not a pull**: WarcraftLogs keeps it in the same `fights` list and marks it with `encounterID == 0`, so `build_fight_list()` skips `encounter_id <= 0` — a trash pack has no boss percentage, no meaningful pull number and no tactic to rate against, but there are dozens of them between the handful of fights worth opening. The bot filters too; this side filters anyway because the list comes from a server that is not updated together with the app. The single-fight endpoint deliberately returns the *exact same JSON shape* as the live endpoint's `"ok"` response, so `snapshot_from_payload()` handles both live and archived fights unchanged (just with `live=False` for the latter). Full contract for all three in `docs/warcraftlogs-bridge.md`; **none of the three bot endpoints exist yet either** — same "reports gracefully as unavailable, mock/live stays usable" story as the live endpoint.

### Replay: playing a finished pull back second by second

The Play button in `ArchivePicker` starts a **replay**. `analyzer/replay/` is the one deliberate exception to "the `RaidSnapshot` is the only contract": a replay needs the whole fight, so `FightTimeline` describes the full course of one. It still never reaches a widget — the only reader is `snapshot_at(timeline, seconds)`, which returns an ordinary `RaidSnapshot`. For WeintTV and the Academy a replay is therefore indistinguishable from a live feed.

That is also where the two modules' synergy comes from for free: because every Academy metric reads the snapshot, the Academy automatically rates the state of the second being shown, with no replay code on its side.

All timeline series are **cumulative**. Seeking then costs the same as playing, and interpolation between samples keeps the boss bar smooth at 8×; from per-tick deltas both would need a running sum from the start. `snapshot_at()` is pure and must never raise — it runs four times a second. What can't honestly be reconstructed per second (consumables, the full per-ability damage breakdown) stays **empty** rather than estimated and only appears at the end from `FightTimeline.aggregate`; per-player-per-ability series would be megabytes per fight, and invented numbers are exactly what makes a deep analysis untrustworthy.

`RaidDataService` grows `MODE_REPLAY` as a third value of the **same** `ArchiveState.mode` field — a second "am I suppressed" flag is how the live poll eventually overwrites a replay frame. `_poll_once()` therefore checks `browsing` (not live) rather than naming the archive mode. The clock is a `QTimer` on the main thread, not another thread: reconstruction is pure computation over ≤25 players, and a thread would have to hand its results back through a signal anyway. It ticks through `_advance_replay(delta)` so tests can step a replay without waiting on a real clock. Every replay frame publishes with `track=False` — the pull number never changes during playback, so tracking would append one history entry per tick. Loading the timeline runs in a short-lived thread with the same stale-result check as the archive fetches.

The clock is never touched directly. Every state change calls `_sync_replay_clock()`, which emits the private `_clockRequested` signal; `_apply_replay_clock()` then **derives** from the state whether the timer should run. Both halves matter and both are scar tissue. A `QTimer` may only be driven from its owning thread, and the timeline loads in a worker — `QTimer.start()` from there is refused by Qt *with a message on stderr and no exception*, so the replay used to sit silently at 00:00 while the state and the UI both claimed it was playing. And the signal must carry no "start/stop" payload: queued from a worker it arrives later, and a stale "start" would wind the clock up for a replay that had already ended. Deriving the answer at delivery time makes a late signal at worst redundant, never wrong.

Five more things the Play button needs, each of which was once missing:

- **`replay_available()` creates the provider instead of only inspecting it.** It runs while a page is being built, long before the poll thread exists — reading `self._provider` there always answered "no" and the button never appeared, because nothing re-asks. Provider constructors do no I/O, so building one there is free.
- **The question is whether the class *overrides* `timeline`**, not `hasattr` — `RaidDataProvider` defines it and returns `None`, so `hasattr` is always true and the button appeared for sources that cannot deliver a replay.
- **Changing report, pull or data source calls `_discard_replay()`.** `start_replay()` treats an already-loaded timeline as "just rewind"; a leftover one from the previous selection meant pressing Play replayed the *wrong* fight — and, since the mode stayed `MODE_ARCHIVE` where `_advance_replay()` refuses to tick, as a still frame. `_discard_replay()` returns to `ReplayState.origin`, not blindly to the archive, so someone who started from the live feed does not get dumped into the archive picker.

- **The timeline is prefetched, but *after* the fight, not beside it.** `_fetch_fight_worker()` starts `prefetch_timeline()` once the fight has arrived (and only if it arrived), so the entire wait still sits *before* the button rather than behind it — Play then normally starts in milliseconds. Running the two in parallel, as it did first, was the defect: both make the bot read the same full event streams of one fight on a 0.15 vCPU host, so the prefetch competed with the very request the user was waiting for, and picking a pull ended in "Bot nicht erreichbar: The read operation timed out" while the bot log showed the fight completing moments later. That makes a click *during* the fetch the likely case rather than the rare one, and `start_replay()` used to answer it by returning silently: `ReplayState.starting` now records the request and `_begin_replay()` honours it when the data lands (one fetch, not two). `loading` and `starting` are therefore different questions — `ArchivePicker` greys the button only for `starting`, because a background prefetch is not something the user asked for. A prefetch that *fails* is logged and otherwise silent for the same reason; the next press asks again and reports the error then.
- **Every archive endpoint gets the timeout its work deserves** — `TIMEOUT` 40 s for the two lists, `FIGHT_TIMEOUT` 180 s for one pull, `TIMELINE_TIMEOUT` 240 s for its timeline. Budgeting the expensive calls like a three-line report list made the most expensive one the tightest, and a timeout there looks exactly like a broken button. Two numbers set the floors: the bot itself waits up to 30 s per WarcraftLogs query, so a client that gives up earlier can never show the bot's own explanation (only its own timeout — the least useful message precisely when the cause lies elsewhere); and one archived pull means tens of thousands of events fetched page by page and folded on 0.15 vCPU, which is minutes, not seconds. `_get()` translates `httpx.TimeoutException` into a German sentence that names the next step instead of passing through "The read operation timed out", and carries the bot's `detail` into the message for non-200 answers.

One trap this uncovered: `SegmentedControl.setValue()` silently does nothing for an unknown value, so `ArchivePicker` must map `MODE_REPLAY` back onto the view it was started from, or the Live/Archive switch freezes on its old state.

A replay ticks at 4 Hz, which turns anything on `replayChanged` or `snapshotChanged` into a per-frame cost. Three consequences, all of which were once real defects rather than mere slowness:

- **`ArchivePicker` must not rebuild its combo boxes on every tick.** It listens to `replayChanged` (the ReplayBar needs it for clock and slider), and `_fill_reports`/`_fill_fights` used to `clear()` and refill unconditionally — an open dropdown snapped shut four times a second, so during playback you could not pick a different pull at all. Both now compare a content signature first.
- **A hidden page must not draw.** Both pages stay connected to `snapshotChanged` for their lifetime, so each was rebuilding itself while the *other* was in front — for the Academy that means a full profile and training plan per frame. `_on_snapshot()` on both pages returns unless `self._attached`; `on_enter()` draws once directly, so nothing is missed.
- **`setStyleSheet()` is not a setter.** Qt discards the widget's cached style computation, re-parses, re-polishes and schedules a repaint even when the string is unchanged — it does not compare. The "build rows once, relabel later" widgets under `gui/widgets/tv/` were re-setting a cell's stylesheet on every relabel although only the text changes; that was ~280 calls and three quarters of the cost of one WeintTV frame (25 ms → 3.5 ms once fixed). `gui/theme/restyle.py`'s `restyle()` is the one place that check lives, and per-frame `apply()` paths use it instead. The same trap in another guise: `ToggleSwitch._animate_to_state()` restarted its animation even when the thumb was already at the target, so the Academy's catalog ran dozens of invisible animations per frame.

Tests that build a `RaidDataService` must shut it down (`tests/test_raid_data_service.py` has an autouse fixture for it). A service left with a running replay holds an active `QTimer`; when Python later collects it during a worker thread's allocation, `~QObject` runs on the wrong thread and the process segfaults. In the app this cannot happen — `CompanionManager` owns the service and calls `shutdown()`.

Live combat-log parsing does not exist yet either: `analyzer/combatlog/` currently contains only `locator.py` (which really does find `Logs/WoWCombatLog*.txt` and is surfaced in Settings → Module). The tailer, event parser and aggregators are the next step; the provider contract is already in place for them.

### Data flow: addon ↔ Companion ↔ Bot

The addon writes outbound messages into its WoW SavedVariables Lua file (`WeintCompanionDB.queue`, parsed by `addon/sync_reader.py` — a hand-rolled line parser, not a full Lua parser, see `core/lua_table.py` for the variable-block extraction helper). `SyncManager.process()` (`core/sync_manager.py`) drains that queue each cycle and, depending on `message["type"]`, dispatches to a different downstream client:
- `"character"` → `CharacterSyncClient` (requires a linked Discord account; silently dropped if unlinked or the "Bridge Card" for it is disabled in settings)
- `"loot"` → dropped unless `loot_sync_enabled` (off by default)
- everything else → the generic `discord.sync_client.SyncClient`

`DiscordRosterSync` (`core/discord_roster_sync.py`) runs the opposite direction: it polls the bot's `/companion/raid-roster` endpoint (bearer-token-authenticated via the stored `companion_token`) and, on new data, publishes a `raid_import` message *into* the addon — this is how the addon receives raid-roster/calendar data from Discord. It runs in the same sync cycle as the material sync but is isolated in its own try/except so a roster-sync failure never blocks material sync or vice versa.

`AddonAnalysisSync` (`core/addon_analysis_sync.py`) is the second inbound sender: it publishes the last analysed `RaidSnapshot` as three messages — `academy_catalog`, `academy_state`, `weinttv_report` — so the slimmed-down in-game WeintTV/Academy in WeintCodex 1.0.1.0 has something to render. Their payloads are **nested tables**, not strings: `core/lua_table.to_lua()` writes real Lua, because a delimiter format is not unambiguous for German lesson text and damage advice. The shapes are built in `addon/addon_payloads.py` and must stay in step with the header comment of the addon's `modules/companion.lua`. Two Companion conventions are passed through unchanged and must never be normalised: `stars == 0` means *no data* (not *bad*) and `at_seconds == -1` means *no timestamp known* (not second 0). The service deliberately never calls `RaidDataService.attach()` — that would make the app poll forever for users who never open either page — so what gets delivered is whatever WeintTV or the Academy last analysed.

`AccessProfileSync` (`core/access_profile_sync.py`) is the third inbound sender and runs **first** in the cycle: it fetches the user's Discord role names from the bot (`GET /companion/access-profile`) and publishes an `access_profile` message, from which WeintCodex 1.2.0.0 derives which areas are open. The bot endpoint does not exist yet — a 404 means "no profile", one log line, and the addon behaves exactly as before 1.2.0.0 (everything open). Same "gracefully unavailable" story as the WarcraftLogs bridge; full contract in `docs/access-profile-bridge.md`.

The role→tier→feature mapping lives in `core/access_roles.py`, deliberately on this side: a role renamed in Discord can be followed without a bot deploy (`config.data["access_role_map"]` overrides the default). Its `build_profile_payload()` is a **pure** function — no `httpx` import — for the same reason `analyzer/providers/warcraftlogs_payload.py` is separate from `core/warcraftlogs_client.py`: it stays testable without network or app. Three rules encoded there:

- **`community.id` must reach Lua as a string.** A Discord snowflake exceeds Lua 5.1's number precision; written as a number it becomes `1.23e+18` and never compares equal to the addon's binding, so every message would be rejected as "foreign community". `tests/test_access_profile.py` checks this against a real Lua interpreter, not just the Python structure.
- **Features are emitted complete and boolean.** The addon treats anything that isn't a real boolean as *unset* and falls back to its own tier matrix; sending all nine keys means that matrix is never needed and the two tables cannot drift apart unnoticed.
- **No tier match delivers nothing**, with a logged reason. A silent fallback to `gast` would turn a config mistake (role renamed, map not updated) into a lockout that looks deliberate.
- **`TIER_FEATURES` must mirror the addon's table** in `core/access.lua`, and must never grant `calendar.view` without `raids.view` — the addon's calendar page reads the roster for its invite preview.

Messages written into the inbox may carry an optional `community` (the Discord guild id, as a string). The addon rejects messages whose community differs from its binding instead of merging them — the point being that switching the linked Discord account in the app must not mix two guilds' rosters into one `SavedVariables` file. Outbound messages carry the same field the other way; `SyncReader.get_messages()` reads it, and `remove_message()` has to write it back, because that function **rebuilds the surviving entries from a fixed field list** — anything it doesn't name explicitly is gone afterwards.

All inbound senders go through `AddonInbox` (`addon/addon_inbox.py`), which keeps one channel per sender and writes the union. `InboxWriter.send_batch()` replaces the *whole* queue (correct, since the addon empties it at login), so without channels the second sender in a sync cycle would silently delete the first one's messages.

The addon's Rotationshelfer reports one `dummy_practice_session` message per finished practice session at a training dummy, handled locally by `core/academy_dummy_sync.py` (never sent to the bot). Three consecutive calendar days with a qualifying session tick the spec's `<slug>.rotation.dummy_practice` lesson. Qualifying means **at least `MIN_SESSION_SECONDS` (180) of combat time** and `MIN_COMPLIANCE_PERCENT`; the duration floor is also enforced in the addon (`MIN_SESSION_SECONDS` in `modules/rotationtrainer.lua`) and the two numbers must stay equal — the addon-side one is what the player sees, this one is what holds when they run an older addon version. The message's seven positional fields are fixed; extending them means touching both sides.

The return path is the outbound `academy` state message: lesson checkboxes ticked in-game come back as `<char>|<done,…>|<excluded,…>;…` and `SyncManager._apply_academy_progress()` replaces the local `AcademyService` lists with them. It never reaches the bot — this is desktop-local data.

### Gear: what "Meine Charaktere" and "Vorbereitung" draw

Both pages were empty through 2.0.0, and that was honest: the app knew *nothing* about gear. The twink list (`"character"`) carries name, class and realm and goes on to the bot; item level, enchants, sockets and open BiS slots appeared nowhere. A progress ring at 0 % would have claimed a measurement nobody took — the same line `stars == 0` draws in the analyzer.

WeintCodex 1.3.3.1 supplies that measurement as `character_sheet`, a fourth local message type (`core/character_sheet_sync.py`, dispatched in `SyncManager`, never sent to the bot — it is the player's own gear, not guild knowledge). Full contract in `docs/character-sheet-bridge.md`. Four things worth knowing before touching it:

- **The addon judges, the Companion draws.** Which enchant is optimal, which gem sits wrong, which stat is over cap — all decided in `modules/charakter.lua`, where spec profiles, caps, socket bonuses and the real item tooltip exist. Exactly the reverse of WeintTV/Academy, and for the same reason: two evaluations of one fact drift apart, and then game and desktop contradict each other.
- **The addon reports one character, `CharacterStore` builds the list.** `character_sheet` is a `STATE_MESSAGE`, so at most one is queued and it always describes the character logged in *now*. The roster across twinks only exists on this side, in `characters.json` under `Paths.config()` — a twink not played for two weeks must still be listed, and in `cache()` the first cleanup would delete him while the page claimed he doesn't exist. A newer report **replaces** an entry rather than merging into it: a field the new report no longer carries describes a state that no longer exists.
- **`None` is not zero, in three places.** `readiness()` returns `None` when nothing was checked (ring stays at 0 but carries a "KEINE PRÜFUNG" chip); `bis is None` means "no BiS list maintained for this spec" and shows "keine Liste" rather than "0 offen"; a slot status of `-` means "this slot has no such thing" (a neck takes no enchant) and is not a defect. **Open BiS slots deliberately do not count toward the ring** — they hang on loot luck, not preparation, and would keep a freshly geared character permanently red for something they cannot fix.
- **Only high-level characters are listed.** Since 2.3.1 both pages and the Overview tile read `CharacterStore.characters()`, which drops everything below `min_level()` (90, MoP Classic's cap, overridable via `characters_min_level` in the config; an unusable value is ignored, not adopted). The pages ask "what do I raid with", and four levelling twinks made the one character that answers it unfindable — a missing enchant on a level 34 alt is the normal case, not an open slot. Four rules with it: hidden is not deleted (`all_characters()` still has them, and `get()` walks that list, or `apply()` would create a second entry per login); the footer **names** how many are hidden and why, since a character that vanishes from yesterday's list is otherwise indistinguishable from a defect; "only twinks reported" is its own empty state, because "the addon has not reported a character yet" would there be plainly false; and a **missing** level counts as high — the 0 means "not reported" (an older addon, a truncated field), and reading it as a twink would turn a data gap into a finding, the same line as `stars == 0`.
- **The version gate needed a third digit.** The addon only sends when `companionVersion` is ≥ 2.0.1; 2.0.0 was already shipped and does not know the type, so `CompanionAtLeast(2, 0)` would have included exactly the version that breaks. That is why the addon's helper grew an optional `patch` argument.

The Overview's `PreparationCard.apply()` reads the same `CharacterStore.preparation_summary()`, so the tile and the page cannot disagree.

**"Meine Charaktere" carries a portrait, and it is the class.** The addon's Charakter page opens with a `PlayerModel` — the character itself, in 3D. That model does not exist on the desktop: the client art lives in CASC rather than as a file, and `character_sheet` carries neither race nor gender to build one from. What it does carry is the class, which is what a portrait answers at a glance anyway, so `gui/widgets/class_avatar.py` draws the class emblem in class colour on a tile tinted the same way, at the same place in the card as the portrait in the game. Three things about it: the eleven emblems under `resources/icons/class_*.svg` are **own drawings** (a copy of Blizzard's would be foreign material in the installer); an unknown class gets the neutral `charaktere` glyph and no emblem, because a guessed one would be indistinguishable from a reported one (`class_icon()` returns `None`, same line as `stars == 0`); and the tile mixes its surface with `tokens.mix()` rather than tinting with `tokens.tint()`, since it is painted and not overlaid. `tests/test_class_avatar.py` renders every emblem and counts opaque pixels — a broken or missing SVG makes `QSvgRenderer.isValid()` `False`, and `tinted_pixmap()` then answers with a fully transparent pixmap: no exception, no log line, just an empty tile for whoever plays that class.

### WeakAuras eintragen, ohne ein Addon-Release zu bauen

Bis 2.0.12 gab es genau einen Weg, eine WeakAura in WeintCodex zu bekommen: eine Lua-Datei unter `data/weakauras/` anlegen, sie in die `.toc` eintragen, eine Version schneiden, ein Release veröffentlichen und warten, bis alle es installiert haben. Der Bereich **WeakAuras** (`gui/pages/weakauras.py`, `PageId.WEAKAURAS`, Gruppe *Charakter*) nimmt sie stattdessen entgegen und stellt sie über die bestehende Addon-Brücke zu; ingame steht sie danach in derselben Liste wie die mitgelieferten. Voller Vertrag beider Nachrichten in `docs/weakaura-bridge.md`.

Die Aufteilung ist die im Haus übliche: `core/weakaura_library.py` ist die **reine** Hälfte (Modell, Prüfung, ID-Bildung, Lesen der Katalogmeldung — kein Qt, kein `httpx`, keine Datei, aus demselben Grund wie `roster_target()` und `build_profile_payload()`), `core/weakaura_store.py` die Ablage in `Paths.config()/weakauras.json` und `core/weakaura_sync.py` der Absender mit eigenem Inbox-Kanal.

Sechs Dinge, die nicht Geschmack sind:

- **Zugestellt wird immer die ganze Liste.** Eine gelöschte Aura verschwindet im Spiel allein dadurch, dass sie in der nächsten Zustellung fehlt — eine Einzelnachricht könnte „es gibt mich nicht mehr" gar nicht ausdrücken, weil das Addon seine Inbox bei jedem Login leert. Deshalb wird auch eine **leer gewordene** Bibliothek zugestellt statt übersprungen (`_delivered_once`), sonst bliebe genau die eine Aura für immer stehen, die weg sollte.
- **Die Kennung wird beim Bearbeiten nie neu vergeben.** Sie entscheidet im Addon darüber, ob eine Zustellung eine neue Aura ist oder eine vorhandene ersetzt. Einen Tippfehler im Namen zu korrigieren darf keine zweite Aura erzeugen. Neue bekommen `companion-<slug>`, damit sie keine mitgelieferte treffen (`DRUID`, `DUNGEONPACK`, …); wer eine mitgelieferte *ersetzen* will, wählt ihre gemeldete Zeile und behält deren ID.
- **Die Liste zeigt auch die mitgelieferten Auren**, obwohl diese Seite sie nicht angelegt hat: das Addon meldet, welche es kennt (`weakaura_catalog`, ab WeintCodex 2.1.0.0, lokal in `LOCAL_MESSAGE_TYPES`). Ohne diese Zeilen liesse sich „aktualisieren" nur auf eigene Einträge anwenden. `addon_entries()` blendet aus, wofür es hier schon eine eigene Fassung gibt — sonst stünde dieselbe Aura zweimal da und es wäre nicht zu erkennen, welche im Spiel gewinnt. **Der Importstring wird nicht mitgemeldet** (das Krieger-Paket allein sind ~56 kB), er bleibt beim Aktualisieren also leer und muss ausgefüllt werden: ein alter String wäre das Gegenteil einer Aktualisierung.
- **„Im Spiel nach dem nächsten /reload" steht auf der Seite**, nicht nur in der Doku. WoW liest seine SavedVariables zur Laufzeit nicht erneut; wer das nicht weiss, sucht die Aura und findet einen Fehler, wo keiner ist. Aus demselben Grund ruft die Seite nach *Fertig* `publish_now()` statt auf den Sync-Takt zu warten.
- **Der Export-String wird von Leerraum befreit, nicht abgewiesen** (aus Discord kopiert bringt er Umbrüche mit, ein WeakAuras-Export enthält selbst keinen), und ein fehlender `!WA:`-Vorspann ist ein **Hinweis**, keine Ablehnung: ältere WeakAuras-Versionen exportieren so. Deshalb sind `validate()` (verhindert das Speichern) und `warnings()` (tut es nicht) getrennt — ein Hinweis, der wie ein Fehler aussieht, wird entweder fälschlich ernst genommen oder lehrt, Fehler zu übersehen.
- **`_fill_editor()` läuft unter einem Riegel** (`_filling`). `setText()` löst `textChanged` aus, das über `_on_edited()` in `_collect()` läuft — und `_collect()` schreibt die Feldwerte in **denselben** Eintrag, aus dem `_fill_editor()` gerade noch liest. Beim Wechsel auf eine andere Aura landete so der Importstring der zuvor bearbeiteten im neuen Formular: sie war halb eingetragen und sah vollständig aus. Und `_render_list()` vergleicht erst eine Signatur, weil `refresh()` bei jeder `state_changed` läuft und ein unbedingtes Neubauen die Bildlaufposition zurücksetzt (dieselbe Falle wie beim `ArchivePicker`).

Seit 2.2.0 geht dieselbe Aura wahlweise **nur auf diesen Rechner oder über den Bot an die ganze Gilde** — `WeakAura.scope`, ein Schalter im Formular. `core/weakaura_client.py` ist die HTTP-Hälfte (`/companion/weakauras`), `core/weakaura_guild_sync.py` der träge Abgleich (600 s), `services/weakaura_library.py` drüben die Bibliothek. Sechs Regeln, jede davon ohne sichtbares Symptom, wenn sie bricht:

- **Freigeben ist eine eigene Handlung, keine Voreinstellung.** Alles, was jemand tippt, ungefragt an 25 Leute zu schicken, wäre die Art Überraschung, die man einmal erlebt und danach die Funktion meidet.
- **Ein nicht erreichbarer Bot löscht nichts.** `set_guild_auras()` wird nur mit einer *erfolgreichen* Antwort gerufen; sonst verschwänden bei jeder Netzstörung alle Gildenauren aus dem Spiel. Eine **leere** Antwort (HTTP 200, `auras: []`) räumt dagegen sehr wohl — genau so verschwindet eine gelöschte oder gesperrte Aura, und dieser Unterschied ist der ganze Punkt.
- **Bei gleicher Kennung gewinnt die eigene Fassung** (`WeakAuraStore.delivery()`): von speziell nach allgemein, dieselbe Ordnung, mit der das Addon eine zugestellte Aura über eine mitgelieferte legt. `shadowed_ids()` sagt es an der Zeile, sonst wäre nicht zu erklären, warum die freigegebene Fassung ingame anders aussieht.
- **Eine vergebene Kennung wird benannt, nicht umgangen.** Der Bot antwortet 409 mit dem bisherigen Autor; erst auf Knopfdruck geht `POST` mit `rename: true` hinaus. Still umzubenennen erzeugte eine zweite Aura, die aussieht wie die erste.
- **Lokal wird immer zuerst gespeichert**, auch bei einer Freigabe: nach einem 409 oder einem stummen Bot wäre die gerade getippte Aura sonst komplett weg. Und **eine gelöschte freigegebene Aura wird auch aus der Bibliothek genommen**, sonst holt sie der nächste Abgleich zurück und die Löschung sähe aus, als hätte sie nicht funktioniert.
- **Die Moderationsknöpfe werden gezeigt, nicht versteckt** — ohne die Raidlead-Rolle erklärt der 403 sich selbst (*lock, don't hide*, wie bei der Charakterzuordnung). Beim Trennen des Discord-Kontos räumt `clear_guild()` die Gildenauren weg; die eigenen bleiben, die hat niemand anderes.

Der Netzteil der Seite läuft in einem kurzlebigen Thread mit Rückmeldung über das Signal `finished` — `refresh()` darf nur zeichnen.

Nicht zu verwechseln mit dem älteren Bot-Import `WCIMPORT:WA:` (`modules/sync.lua` im Addon): der trägt nur Metadaten, **keinen** Importstring, liegt unter einem eigenen SavedVariables-Schlüssel und bleibt unverändert.

### Wer steckt hinter einem Discord-Konto? (`core/character_links.py`)

Der Kalender-Invite in WeintCodex lädt **echte Charakternamen** ein. Der Bot kannte sie nur von Spielern, die die Companion verknüpft *und* ihre Twinkverwaltung gepflegt haben — für alle anderen schickte er den **Discord-Anzeigenamen** weiter, den es im Spiel nicht gibt. `C_Calendar.EventInvite` läuft dort ins Leere und meldet den Fehlschlag nicht, also zählte die Einladung sogar als gelungen mit; die Lücke fiel frühestens am leeren Kalender auf. Gildenfremde können die Companion kaum nutzen, für sie war das kein Übergangszustand.

Der Bot hat dafür seit `services/character_links.py` eine zweite Quelle — eine von Hand gesetzte Zuordnung — und drei raidlead-gebundene Endpunkte (`GET/POST/DELETE /companion/character-links`). Die Seite **Charakterzuordnung** (`gui/pages/character_links.py`, `PageId.CHARACTER_LINKS`) ist die zweite von zwei Stellen, an denen sie sich pflegen lässt; die andere ist `/weintcharakter` in Discord. Beide schreiben dieselbe Tabelle.

Die Aufteilung ist dieselbe wie beim Ausrüstungsbogen, nur mit dem Bot in der urteilenden Rolle: **der Bot entscheidet, diese Seite zeigt an.** Welcher Name gewinnt, wenn Meldung und Handeintrag sich widersprechen, steht ausschliesslich drüben — und auch das Zerlegen von „Njiah-OokOok" in Name und Realm. Die Antwort auf ein `POST` nennt den gespeicherten Stand, und genau der wird angezeigt; zwei Zerlegungen derselben Eingabe würden auseinanderlaufen, und der Unterschied fiele erst am Kalender auf. `core/character_links.py` ist deshalb rein (kein Qt, kein `httpx`, wie `roster_target()` und `build_profile_payload()`), `core/character_links_client.py` die HTTP-Hälfte.

Vier Dinge daran sind nicht Geschmack:

- **Die Seite wird gesperrt, nicht versteckt.** Ohne die Raidlead-Rolle antwortet der Bot mit 403; das ist keine Störung, sondern eine Antwort, reist als eigenes Feld (`Overview.forbidden`) und wird zu einer Erklärung, wofür die Seite da wäre. Dieselbe Regel wie im Addon (`core/access.lua`: *lock, don't hide*) — ein Bereich, der je nach Rolle verschwindet, lässt sich weder erklären noch danach fragen. Das erspart der Navigationsspalte zugleich eine Sichtbarkeitsbedingung, die es dort noch nie gab.
- **„0 offen" wird nie behauptet, wo nichts gezählt wurde.** Ohne laufende Anmeldung sagt `summary_text()` das, statt eine Null zu nennen — dieselbe Linie wie `stars == 0` und `readiness() is None`.
- **Nach dem Schreiben wird der ganze Stand neu geholt**, statt die eine Zeile lokal nachzuziehen. Der Bot entscheidet über den Vorrang; eine lokal geänderte Zeile könnte etwas anderes zeigen, als der Export gleich verwendet.
- **Jeder Abruf läuft in einem kurzlebigen Thread** und meldet sich über ein Signal zurück (`loaded`), weil Widgets nur im Hauptthread entstehen dürfen — dasselbe Muster wie `ConnectionsPage.sync_now()` und die Archiv-Abrufe. `refresh()` zeichnet ausschliesslich, `on_enter()` holt: die Anmeldung ändert sich zwischen zwei Besuchen ständig, und ein veralteter Stand behauptet hier geschlossene Lücken.

### A card that is empty must say whether it was asked

`RaidSnapshot.has_analysis` is an OR across every deep-analysis field: as soon as the source delivers *any* of them it is true and the explanatory paragraph above WeintTV's analysis area disappears. That is precisely when the most common case slips through — the source delivers part of the block and not the rest. What is left is one card's placeholder, and "Keine Raid-Cooldowns erkannt." is indistinguishable from "the raid fired none".

`block_gap_text(snapshot, block)` in `gui/widgets/tv/analysis_gap.py` closes that: it is silent when the block has rows (nothing to explain) and silent when the deep analysis is missing entirely (the area paragraph already says it), and otherwise names the source and states that *this* block was not delivered while others were. Four blocks use it — `movement`, `cooldown_usage`, `raid_cooldowns`, `heal_cooldowns`, the four that reliably come up empty when the bot's `Casts` path fails, since all four derive from it (`events(dataType: Casts)` for the first two, `table(dataType: Casts)` for the other two). The Companion side of those four is provably correct: a contract-shaped payload produces all of them (`tests/test_warcraftlogs_payload.py`), so an empty card is a delivery question, not a mapping question.

### Who is "me"? (character identity, `analyzer/names.py` + `core/character_report_sync.py`)

This question had **four independent answers** and nothing reconciled them: the combo box in `gui/pages/academy.py`, `config["academy_player_name"]`, `PlayerProfile.name`, and `UnitName("player")` in-game. The one reliable source — the logged-in character — was never asked, so the app *guessed* from a WarcraftLogs roster and the addon adopted the guess unchecked. Symptom: picking a character on the desktop showed an old or a completely different one in-game.

- **The selection never guesses.** `resolve_player_name()` returns what is stored, or `""`. The guess is `suggest_player_name()`, reachable only through `ensure_player_name()`, which **persists** it. A guessed identity must never reach the wire — what goes to the addon is always something the user has seen.
- **`reconcile_selection()` decides *and* stores.** It is the single place the roster combo's content is settled, deliberately on the service rather than in the page so it is testable (nothing in `tests/` builds a widget). The original defect was a missing `else`: the page refilled the combo and only restored the selection *if* the stored name still occurred, leaving the box on `names[0]` while the config kept the old name — and the payload is built from the config.
- **The roster's spelling wins.** `match_name()` returns the *list's* spelling, not the candidate's, because `evaluator.find_actor()` looks the actor up by exactly that string. `analyzer/names.py` holds the three comparison rules; a **missing realm is a wildcard, not a mismatch** (the client only ever knows the bare name, WarcraftLogs only qualifies cross-realm rows). The addon carries the same three rules in `core/names.lua` — they must stay identical, or "me" in the game is someone else than "me" on the desktop.
- **One identity per delivery.** `AddonAnalysisSync.process()` resolves the name **once** and passes it to `build_profile`, `build_academy_state(character=…)` and `build_weinttv_report`. Before that, `academy_state.character` came from `PlayerProfile.name` — which is literally `"-"` when the player isn't in the snapshot — while `weinttv_report.me` carried the real name. `build_plan(character=…)` takes it too, or progress would be looked up under that same non-name. `hasActor` says whether the character was in the pull at all; delivering with `hasActor = false` is correct, since `stars == 0` already means "no data".
- **A selection change publishes immediately.** `set_player_name()` calls `addon_analysis_sync.publish_now()` (`invalidate()` + `process()`). The `getattr` guard there is load-bearing: `AcademyService` is constructed in `CompanionManager.__init__` *before* `AddonAnalysisSync`. The fingerprint is also invalidated when `detect_wow()` sees a different `wow_path` — it knows content, not destination.
- **The game reports who is logged in.** WeintCodex 1.3.3.0 sends `character_report` (`<Name>|<Realm>|<classFile>|<Level>|<specKey>`, two to five fields tolerated). It is handled locally like `academy` and `dummy_practice_session` and **never reaches the bot** — deliberately a new type rather than widening `character`, which is a bot contract. `note_ingame_character()` then follows it, with one rule: **a manual pick beats the game report for the character it was made on, and stops beating it the moment the game reports a different one** (`academy_manual_for`). Otherwise "I looked at Bob's numbers while playing Alice" would still be in force when logging in as Carol.
- **`InboxWriter` writes `companionVersion` on every batch, including an empty one.** The addon reads it and only sends `character_report` from 1.7.0 on. Without that, an older Companion would drop the unknown type into its generic branch, POST it to the bot, fail, never remove it, and log an error every five seconds. Release-order advice would not have fixed this — addon and app update independently.
- **The WeintTV player picker stays a display filter.** It has an `ALL_PLAYERS` value with no Academy equivalent, and the raid view exists to look at *other* people; re-pointing the in-game "me" at a colleague glanced at once would recreate the very bug. The explicit path is `playerRequested` → `open_academy_for()` → `show_player()` → `note_manual_choice()`. A muted line next to the picker names the current Academy character so the divergence is visible where it is created.

The bot backend base URL is centralized as `BOT_BASE_URL` in `core/backend_config.py`, imported by `core/discord_auth.py`, `core/character_sync_client.py`, and `core/discord_roster_sync.py`. The same file holds the project's Discord guild and its feedback channel, because two places need the guild: the support link in Settings → Über and the Overview's "Aufstellung im Discord" button, which was wired to nothing at all. `roster_target()` decides where that button goes and is deliberately **pure** — no Qt, no `httpx` — for the same reason `access_roles.build_profile_payload()` is: the decision is where something can be wrong, so it stays testable without a window. Its order carries the point: a guild named by the access profile wins, because only that one demonstrably belongs to *this* user; with an account linked but no guild reported (the endpoint does not exist yet) it falls back to the project's guild; with nothing linked it opens Settings → Discord rather than a server the app has never talked to. `AccessProfileSync` stores the guild in `config["discord_community_id"]` as a **string** — a Discord snowflake exceeds float precision and would come back as `1.23e+18` — and it stores it *before* the "nothing changed" fingerprint short-circuits, or the link would be missing on every start where the profile is unchanged, i.e. almost always.

**Opening a URL goes through `core/browser.py`, never through a bare `webbrowser.open()`.** In an AppImage/PyInstaller bundle the browser inherits our own `LD_LIBRARY_PATH` and dies with a symbol lookup error the moment it starts; `Runtime.clean_environ()` exists for exactly that. Two of the three call sites used it and the third — the Overview's "Aufstellung im Discord" button — did not, so that button did nothing at all: no window, no exception (`webbrowser.open()` only sees that it launched a helper), no log line. A rule followed in two of three places is a reminder, not a rule, which is why it is now a function. `open_url()` also reports the "no browser found at all" case, where `webbrowser` returns `False` without raising, by logging the address so it can be opened by hand.

### The next raid on the Overview

The countdown chip read "KEIN TERMIN BEKANNT" permanently, and not out of caution: it was built once and never touched again. What the app knew of the guild calendar were the two opaque WCIMPORT strings `DiscordRosterSync` passes straight to the addon — and `/companion/raid-roster` requires the raidlead role, so parsing them would have shown the date to exactly one person.

The bot therefore answers that question separately: `GET /companion/raid-schedule` (`services/raid_schedule.py` over there), for **any** linked user, carrying the appointment and the sign-up counts but deliberately no names — that much is in the sign-up embed anyone in the channel can read, while the name list stays behind the role. `core/raid_schedule.py` is the pure half on this side (parse, compute, label; no Qt, no `httpx` — same reason as `roster_target()` and `build_profile_payload()`), `core/raid_schedule_sync.py` the HTTP half, running in the ordinary sync cycle and caching its answer under `Paths.cache()` so a start without a reachable bot still shows the last known date. Three rules it holds: a missing date stays missing (no invented Wednesday — it would be indistinguishable from a real one); the **offset comes from the bot** in `starts_at`, so the remaining time is computed against the local clock rather than a guessed timezone; and "zugesagt" counts `active` only, with "vielleicht"/"Ersatzbank" named beside it instead of folded in. A 404 means an older bot and is silent — the Overview then says what it always said.

**Fetching it is not showing it, and the interval belongs to the sign-ups rather than the date.** Two things were wrong with the 5-minute fixed tick through 2.3.2. First, nothing redrew: the fresh roster sat in `RaidScheduleSync.schedule` while the card kept the numbers it had, because a page's `refresh()` hangs off `change_page()` and `state_changed`, and neither fired. `process()` now **returns whether the answer changed**, `_run_sync_worker()` collects that (together with `UpdateWatch`'s) into one `dirty` flag and emits `state_changed` once at the end — only when something moved, since a signal per tick would redraw the visible page every five seconds. Second, the *date* changes once a week but the *sign-ups* change by the minute on raid day, and that is precisely when someone looks: `refresh_interval(schedule)` (pure, in the same module, for the same reason `parse_schedule()` is) answers 60 s from `SOON_MINUTES` before the pull until `is_running()` stops being true, and 300 s otherwise — no known date means the slow tick, because a minute cadence for an answer that does not exist buys nothing. Two details follow: the comparison is now against the **whole** frozen `RaidSchedule` rather than `known`/`days`/`title`, so a closed sign-up (`signup_status`), a changed target composition, a changed raid size or a second parallel raid also reach the screen — all of them are on the card and all of them used to be silent; and the log line stayed on the *appointment* (`_appointment_keys()`), or raid evening would write "Raidtermin übernommen" into the protocol once per sign-up. "Erneut prüfen" on the Overview calls `raid_schedule_sync.invalidate()` too — the button sits next to the roster, so it means everything the page shows — but does not fetch there: the next sync tick, at most five seconds later, does.

**The bot's base URL is overridable, and that is not a nicety.** All ten call sites read `BOT_BASE_URL` from `core/backend_config.py`. The bot is hosted somewhere that picks the machine the app runs on and writes that machine into the hostname — so a forced move (the build server was unavailable for hours, the app had to be recreated elsewhere) changes the address while nothing about the bot itself differs. Hardcoded, every such move costs a Companion release that everyone must install first, and until then not one install reaches the bot. `resolve_bot_base_url()` therefore checks `WEINTCODEX_BOT_URL` in the environment, then a `bot_url.txt` in the config directory, then the built-in default; an unusable value is **ignored rather than adopted**, because a broken address fails every single call silently and the built-in value is still the better guess. It deliberately does not use `Paths.config()` — that function creates the directory, and a module import must not create directories in the user's profile. Two clients (`discord/sync_client.py`, `core/discord_status.py`) used to carry their own copy of the address and were promptly left behind on the old host by that move; they route through the constant now.

Since 2.0.11 several raids may run **at once** in Discord (a 10-man for mains beside a 25-man for twinks). The Overview has exactly one slot for the appointment, so the response shape did not change: every top-level field still describes one raid — the one starting soonest — and the rest arrive as `others`, an optional list whose entries carry the same fields minus `status`. That was a deliberate choice against a list at the root, which would have blinded every shipped Companion at once; an older build simply ignores a field it doesn't know. `_parse_others()` therefore runs each entry back through `parse_schedule()` rather than rebuilding it — a second data type would eventually compute differently from the first — and strips `others` from the nested entry, or the response would dictate the recursion depth. `others_text()` renders the one line the Overview shows under the composition; without it a parallel raid would be invisible in the app, and nobody would learn they could sign up elsewhere. The contract's line holds for `others` too: titles, sizes, appointments and counts, never names.

The chip is redrawn by a one-minute `QTimer` started in `on_enter()` and stopped in `on_leave()`, because the label is coarse by design (days → hours → minutes) and a per-second repaint would be work with no picture. That same tick also carries the greeting below.

**The header greets, and it says when the raid is.** Until 2.0.7 the Overview's head was two fixed strings — the eyebrow "HEUTE" and one of three sentences about the *installation* ("Alles bereit für den nächsten Raid.", "Für das Addon liegt eine neue Version bereit.", "World of Warcraft wurde noch nicht gefunden."). That is the same mistake the Overview cured the old dashboard of, one storey up: the spot everyone reads first says something they already know, identically for every user at every hour. `core/greeting.py` replaces it — daypart plus name in the eyebrow, the next raid in the title — and is pure (no Qt, no `httpx`), for the same reason `raid_schedule.py` and `roster_target()` are: *which* sentence stands there is where something can be wrong. Five rules:

- **The name is never guessed.** It comes from `academy_ingame_character` — what the addon reports about the character actually logged in — then the Discord username, then nothing (`AppState.discord_name` starts as `"-"`, which means "unknown", not a name). Deliberately **not** `academy_player_name`: that is the Academy's selection and may sit on a colleague whose numbers were looked at once (see `analyzer/names.py`).
- **Days are calendar days, not 24-hour blocks.** At 23:00 a raid the next evening is *morgen*, though only 21 hours away — `days_until()` therefore subtracts dates. Beyond `MENTION_DAYS` (6) the head says nothing about it, and without a date the old sentence stands: an invented Wednesday would be indistinguishable from a real one.
- **The title is one line, 28 px, and gets cut off — not wrapped — at `WINDOW_MIN` (960 px).** Hence a pending update only rides along as a half-sentence when the raid is at most two days out, and then the clock drops out of the phrase (`raid_phrase(clock=False)`). `tests/test_greeting.py` pins the longest producible title against the longest one 2.0.7 could already show, so the line cannot grow back unnoticed.
- **The raid outranks the update in the title**, because the update card sits directly beneath it, names both channels and carries the button — three other places already announce a waiting update (system row, nav badge, toast).
- **The minute tick redraws it**, so "Morgen ist Raid" becomes "Heute" at midnight and "Guten Tag" becomes "Guten Abend" at 18:00 in an app that stays open all evening. `PageHeader.setEyebrow()` compares before setting, like `setTitle()` — `QLabel.setText()` does not.

**"Erneut prüfen" also sits on the Overview**, next to the countdown, and runs the same `refresh_update_status()` as the button under *Addon & Updates*. It belongs here because this is the page that *announces* a waiting update and was the only one where you could not ask again. It runs in a short-lived thread (same pattern as `ConnectionsPage.sync_now()`): a network round in a click handler freezes the window for its duration, and the result reaches the page by itself through `state_changed`. `refresh_update_status()` now drops both release caches first (`GitHubUpdater.invalidate_cache()`): the 15-minute cache is right for the background tick and wrong for a button, where a user who just heard about a new version would get the answer from ten minutes ago — indistinguishable from a broken button.

**"21 von 25" is a number, not the answer.** The question people open Discord for is *who* is missing — four open slots are harmless if they are damage and a cancelled evening if one of them is the second tank. The card therefore draws the composition the way the 2.0 draft always had it: one row of slots per role, filled ones in class colour, open ones as a gap, and a sentence underneath ("Vier offene Plätze · 1 Heiler, 3 Schaden"). `days[].roster` carries **role and class per sign-up, never a name** — both are visible as symbols in the sign-up post anyone in the channel can read, so the contract's line stays exactly where it was; `composition` is the target strength per role. Three fallbacks, in the same "never guess" spirit as `stars == 0`: without `roster` there is **one** strip labelled "ZUGESAGT" instead of three estimated ones (three guessed rows would be indistinguishable from three reported ones); without `composition` the sentence stops at "Vier offene Plätze" rather than claiming which; and what is left over after the per-role gaps is "frei wählbar", because a target says how many healers are needed, not how the last seat must be filled. `gui/widgets/roster_strip.py` paints the whole thing in one `paintEvent` (25 slots as 25 widgets would be 25 layout objects rebuilt on every sign-up) and reads the accent *while painting*; its one non-obvious rule is that a row is never narrower than its own caption — two tanks are 22 px, "TANKS" is more than twice that, and without the floor the next caption overprinted the previous one ("TANKSHEILER").

**"Dein letzter Pull" must survive a restart.** The card read `RaidDataService.history()` alone, and that list only fills with pulls completed **in this session** while WeintTV or the Academy was open — so the morning after a raid it said "Noch kein Pull", which is not caution but a wrong statement: the fight happened, the app looked in the wrong place. `core/last_pull.py` (pure) plus `core/last_pull_sync.py` (HTTP) add the second source: the newest WarcraftLogs report with a boss fight, through the same three archive endpoints the Archive mode uses, every 20 minutes, cached under `Paths.cache()`. Four things worth keeping: the **session wins** over the archive (a pull that just ended is the last one even if WarcraftLogs has not seen it yet); the **fight list is enough** — boss, outcome, duration and pull number are already in it, while the single-fight endpoint costs the bot minutes, so the card says outright that an archived pull carries no rating instead of estimating one; the trend line holds only pulls of the **same** boss; and `time.monotonic()` counts from boot, so a `0.0` "last fetched" would suppress the first fetch entirely on a machine that booted minutes ago (both this sync and `RaidScheduleSync` use `None` for "never"). The second half of that bug was silent in a different way: the card read `boss` and `boss_percent` off `PullSummary` via `getattr` with a default, and those fields are called `encounter_name`/`boss_health_percent` — so even a filled history showed "Kampf" without a curve.

**The bot's database is not the authority on whether a raid exists — Discord is.** Delete the sign-up message by hand (right-click → delete) instead of through "Raid löschen" and the bot never notices: the record stays and every reader treats it as the running sign-up. In Discord that is invisible (the message is gone), but the Overview then named a long-deleted test raid as the next appointment, after every restart. The endpoint therefore looks in Discord before it answers (`locate_signup()` / `SIGNUP_PRESENCE_SECONDS` in the bot), and the doubtful case counts as *present* — only an explicit `NotFound` for **every** known message means the sign-up is gone, because a briefly unreachable API must not hide a running raid. The same answer carries the `discord` block (guild, channel, message of the sign-up), which is what `roster_target()` turns into the "Aufstellung im Discord" target; `DISCORD_RAID_CHANNEL_ID` is only the fallback for an older bot, and only inside the project guild — a foreign guild has its own channels.

**A Discord link goes to the Discord app first, the browser second.** `open_url()` takes an optional `app_url` (`backend_config.app_url()` rewrites `https://discord.com/channels/…` to `discord://-/channels/…`) and tries it before the browser, because the button would otherwise land in a second, usually logged-out view of the same server while the app sits open next to it. The hard part is the fallback: someone who uses Discord in a browser only has no program for that scheme, and a silently swallowed launch would be exactly the dead button `core/browser.py` was written against.

**The system opener's exit code is not the answer to "is there a program for this scheme?" — on Linux.** `os.startfile` raises on Windows and `open` returns non-zero on macOS when nothing is registered, so both are trustworthy. `xdg-open` is not: with no `x-scheme-handler/discord` registration it hands the address to the **default browser** and still reports 0, and the browser turns `discord://-/channels/…` into `http://discord//-/channels/…` — a link that exists nowhere. That was the whole bug, and it looked like a wrong URL rather than a wrong question. `core/discord_app.py` therefore asks *before* launching, and `open_app_link()` delegates every `discord:` address to it: read the registered handler's `.desktop` file and accept it only if its **`Exec` line** names a Discord client (Firefox writes a `userapp-Discord-XXXX.desktop` whose Exec is Firefox, so the file *name* proves nothing); otherwise locate the app itself — PATH binary, Flatpak, known `.desktop` entries, an AppImage in the usual folders, including the one this AppImage was started from. Found nothing means `False` and the browser gets the **https** address, which works there. The launch is `Popen(start_new_session=True)`, never `run()`: Discord is a window, not a command, and `run()` would block the main thread until the user closes it. A running instance takes the address through its single-instance lock and switches to the channel.

### A finished check has to reach the screen by itself

`CompanionManager.state_changed` is emitted at the end of `full_refresh()` and `refresh_update_status()` — in a `finally`, so a failed step still reports what the earlier ones already changed. Anything added to that `finally` must therefore be unable to throw, which is why `_note_update_check()` reaches for the watch through `getattr`: the one job of that block is that the report goes out. Since 2.3.3 it is also emitted at the end of `_run_sync_worker()`, but **only when a step reports an actual change** (see below). `MainWindow._on_state_changed()` then redraws the **visible** page and the navigation column.

Without it the update display was, in practice, never right on first sight: `refresh()` hung solely off `change_page()`, while `full_refresh()` runs in `InitThread` and finishes about a second *after* the Overview has been drawn. Nothing asked again, so the system row showed the pre-check state until the user left the page and came back. The signal is deliberately emitted from the worker thread — `CompanionManager` is created on the main thread, so a cross-thread connection is delivered through the receiver's event loop (same reasoning as `_AutoSyncStarter`); calling `page.refresh()` from the thread would touch widgets from the wrong one.

Three places now say that an update is waiting, because one of them is only visible if you happen to be looking at it:

- **The Overview's system row** — `addon`/`app` go to `warn`, the row grows (`motion.expand`) and offers "Öffnen".
- **A badge on "Addon & Updates"** in the navigation column — the only hint visible from WeintTV, the Academy or anywhere else. `NavItem.setBadge()` had existed since 2.0 with no callers at all. It carries a **number**, because the two update channels are independent and "2" saves asking whether both are meant. A *missing* addon is not counted: there the installation is outstanding, which the system row says in its own words, and a "1" would claim an update where nothing is installed yet.
- **A toast**, once per version per channel (`_announced_updates`). `notify()` had also never been called. The memo stores the version rather than a bare "already told", so the *next* version is announced again; without it a second check would repeat the same message, and `state_changed` arrives on every press of "Erneut prüfen" — and, since 2.3.3, from the background watch as well, i.e. without anyone having asked.
- **A tray balloon**, but only while the window isn't on screen (`_announce_in_tray`). A toast in a window nobody is looking at is not a notification, and "minimize to tray" is exactly the mode in which a release can sit there for hours. `isVisible()` alone is not the question — a window minimised to the taskbar still counts as visible to Qt and is just as gone for the user. `messageClicked` restores the window and opens *Addon & Updates*, because a hint you cannot click is one the user has to go looking for; and `showMessage()` is wrapped, since not every Linux desktop can produce balloons at all.

**Nobody asks, so the app has to.** Until 2.3.2 the check happened exactly twice — at startup in `InitThread`, and on "Erneut prüfen". All three announcements above hang off `state_changed`, and after startup that signal simply stopped arriving: whoever opened the app in the morning and raided with it in the evening never heard about a release published at noon. `core/update_watch.py`'s `UpdateWatch` is the missing third trigger. It rides the ordinary sync cycle with its own `try/except` like every other step, but only actually checks every `REFRESH_SECONDS` (900 — the same span `GitHubUpdater` caches for). Four rules:

- **It reports the change, not the check.** `process()` compares a signature of what the UI shows (both versions, both "waiting" flags, the installed addon version) before and after, and returns whether it moved. Emitting `state_changed` per tick would redraw the visible page every five seconds and walk `_announce_updates()` just as often.
- **It drops both release caches first**, exactly like `refresh_update_status()` does. With an equally long interval the cache would keep answering and the check would be one that can never learn anything new.
- **It counts checks made elsewhere.** `full_refresh()` and `refresh_update_status()` call `note_checked()`, or the watch would set off again five seconds after startup against the two endpoints that were just queried.
- **It re-reads the installed addon version.** An update can also disappear because the addon was updated from outside (a second machine, an addon manager); without `detect_addon()` in the same round, "Update verfügbar" would stand until the app is restarted.

**A page's `refresh()` may only draw.** `ConnectionsPage.refresh()` began with a blocking `manager.full_refresh()` — a full network round (GitHub, Discord, sync) on the main thread, in a method that `change_page()` calls on every entry and that the page's own constructor calls too, so the window froze whenever you opened "Verbindungen". With `state_changed` in place it became an infinite loop: the check reported its new state, the window redrew the visible page, the page checked again — 826 GitHub requests in a run that needs seven. The check moved to `sync_now()` and into a short-lived thread; `MainWindow._on_state_changed()` additionally carries a re-entrancy guard, because that failure starts in one page and takes the whole window down. `tests/test_update_visibility.py` holds both halves: the guard, and an AST check that no page's `refresh()` calls `full_refresh()`/`refresh_update_status()`.

### GitHub-based updates (two independent update channels)

- **Addon updates**: `GitHubUpdater` (`core/github_updater.py`), configured in `CompanionManager` against `daddler/WeintCodex`, polls the GitHub Releases API (15-minute cache) and picks the release asset by OS (`.appimage`/`setup.exe`/`.dmg`, or an explicit `asset_filter`). Version comparison uses `normalize_version()` (case/`v`-prefix-insensitive) between the addon's own reported version and the latest GitHub tag.
- **Companion self-update**: `CompanionUpdater` (`core/companion_updater.py`) checks/updates WeintCompanion itself, with OS-specific runners (`linux_updater.py`, `windows_updater.py`).

Both channels are triggered through **one** `UpdateRunner` (`gui/controllers/update_runner.py`), owned by `MainWindow` and handed to any page that exposes `set_update_runner()` (duck-typed in `_ensure_page()`, same as the cross-page signals). It exists because the Overview's update banner and the Addon page both start the same two flows, and each carries a detail that is easy to get wrong a second time: the addon install is deliberately blocking on the main thread with a `processEvents()` in front so the "lädt" state is actually painted; the Companion update runs in a thread, must call `stop_auto_sync()` **before** it (that touches a main-thread `QTimer`), has to restart auto-sync on failure, and quits the process on success. One runner also means one busy flag — two pages cannot start two installs into the same folder.

### Every release ships its changelog — this is not optional

**A release whose body is empty is a bug.** The addon's releases were created by hand with the notes field blank, so the Addon page showed "Keine Änderungen gefunden." forever — accurate and useless, since `CHANGELOG.md` was maintained the whole time. The Companion's own card was no better: it listed **commit subjects** (`GitHubUpdater.get_release_commits()`), which are written for whoever wrote them.

The rule now holds in both directions:

- `CHANGELOG.md` in this repo is the single source. `scripts/check_version.py` (CI, before the build) already fails a tag whose section is missing, and `scripts/release_notes.py` prints that section as the GitHub release body — `build.yml` uses `body_path:` instead of `generate_release_notes: true`. Headings are `## 2.0.1`.
- The **addon's** `CHANGELOG.md` travels inside its release ZIP and therefore lands in the addon folder on every update. That is what `core/changelog_source.py` reads, so the app has the addon's *full* history offline and never depends on the release text at all. Its headings look different (`## [1.3.3.1] – 2026-08-11`), which is exactly why `core/changelog_reader.py` understands both shapes — `tests/test_changelog.py` holds that, because a parser that quietly stops matching produces an empty list, and an empty list is indistinguishable from "nothing changed".

Three consumers read from that one place, and none of them may grow its own parser: the "Was ist neu" popup (`read_changelog_sections()`), the two component cards under *Addon & Updates* (`latest_entry()`), and the changelog view (`gui/dialogs/changelog_dialog.py` — both components, every version, reachable from the Overview banner and from either card). `core/changelog_source.py` decides the order of sources and is where a new one belongs: the component's own `CHANGELOG.md` first, the GitHub release text only as a stand-in for a version built before this rule. **Neither of them is fetched while drawing** — the release text is already in `AppState` by then, and a page's `refresh()` may not go to the network.

`format_changelog_body()` strips Markdown rather than rendering it: a `QLabel` would need every `<` and `&` in the text escaped for rich text, and the changelog is prose written by hand. It has to handle three shapes — `### Neu` subheadings (the addon's), `- ` bullets with indented continuations, and free paragraphs (this repo's, which the original bullet-only version dropped entirely).

### Platform-specific paths and Qt workarounds

`core/paths.py` centralizes all on-disk locations (config/cache/downloads/backups/logs/reports), branching on `platform.system()`: `~/.local/share/WeintCompanion` on Linux, `%LOCALAPPDATA%/WeintCompanion` on Windows. Rule of thumb for new files: anything reproducible goes under `cache()`, anything the user would be upset to lose goes under `config()`.

**Never hand one Qt event handler another one's event.** `OverlayWindow.closeEvent()` called `self.hideEvent(event)` to reuse the detach logic, which passed a `QCloseEvent` down to `QWidget::hideEvent(QHideEvent*)`; Qt reads that pointer as a `QHideEvent` unchecked, and closing the overlay ended the process with SIGSEGV — **no Python exception, no traceback**, which is why no amount of "does it raise?" testing found it. Shared teardown belongs in a plain method that takes no event (`OverlayWindow._release()`), and that method has to tolerate being called twice, since `close()` also produces a hide on some platforms — double-detaching would push the service's reference count below the number of real subscribers and stop the poll thread while WeintTV is still watching. `tests/test_overlay_window.py` covers it; that the process reaches the assertion at all *is* the assertion.

**The splash must repaint itself, never run the event loop — and nothing modal may open before the main window is visible.** `app.py` builds `MainWindow` behind the splash and used `app.processEvents()` to advance the progress bar between stages. `MainWindow.__init__` meanwhile scheduled the startup popups with `QTimer.singleShot(0, …)`, commented "so the window becomes visible first". It did the opposite: the 0 ms timer fires in the *next* `processEvents()`, which is the one inside `_stage(0.85, "Übersicht wird gezeichnet …")` — i.e. **before** `window.show()`. `show_whats_new_if_needed()` opens a modal dialog after every update, `exec()` sits in its own event loop, the splash is `WindowStaysOnTopHint` and its `close()` comes after `show()` — so on Windows the dialog waited invisibly under the splash and the app hung at exactly that progress label, with no crash, no log line and no way out but Escape. Three things now make that state impossible rather than unlikely: `_stage()` calls `splash.repaint()` (synchronous paint, runs nothing else) instead of `processEvents()`, of which exactly one remains — right after `splash.show()`, before any `MainWindow` exists to queue anything; the popups hang on `MainWindow.showEvent` (guarded by `_startup_popups_queued`, since `showEvent` also fires on every restore from the tray), because "when the window is up" is a question only the window can answer; and `splash.close()` runs before `_show_main_window()` hands control back to the loop. `tests/test_startup_popups.py` holds all three plus the end-to-end order on a real `MainWindow`, and pins the Qt property the fix rests on (a `repaint()` does not run a pending timer, a `processEvents()` does). A progress bar is there to draw, not to get work done.

One Qt rendering trap worth knowing: the global stylesheet sets `QWidget { background: transparent; }`, so any widget that must paint its own background needs `setObjectName(...)` + `setAttribute(Qt.WA_StyledBackground, True)` + an ID-scoped rule. And at ~10px, QLabel's computed height clips the dots on capital umlauts ("NÄCHSTE" renders as "NACHSTE") — small mono eyebrow labels should therefore be created with `gui/widgets/eyebrow.py`'s `eyebrow_label()`, which measures the real ink extent and sets a minimum height.

`app.py` sets up crash diagnostics and several Linux/Qt workarounds *before* importing PySide6 — read the inline comments there before touching Qt platform env vars, they encode hard-won fixes for real crash reports:
- `faulthandler` writes native (non-Python) crash tracebacks to `cache/logs/crash.log`, since a SIGSEGV in Qt's xcb plugin never raises a Python exception.
- `QT_QPA_PLATFORM=wayland;xcb` lets Qt itself choose, rather than the app guessing from `XDG_SESSION_TYPE`.
- `QT_XCB_NO_XI2`, `QT_ACCESSIBILITY=0`, `QT_XCB_GL_INTEGRATION=none` are always-on mitigations for distro-specific xcb SIGSEGVs (libxkbcommon/AT-SPI/Mesa), each individually escape-hatchable via `WEINT_FORCE_*` env vars for users the mitigation itself breaks.

### Config and auth

`core/config.py` is a flat JSON-backed settings store (`config.json` in `Paths.config()`) with a defaults dict merged on load so new settings get backfilled into existing installs. Discord account linking is fully implemented: `core/discord_auth.py`'s `DiscordAuth.login()` runs the real OAuth2 flow (local callback server, system browser to Discord, code exchange against the bot's `/companion/auth/exchange`), and `core/discord_account.py`'s `DiscordAccountStore` persists the resulting identity plus a bot-issued `companion_token` (never the real Discord OAuth token) to `discord_account.json`. That `companion_token` is the bearer credential used everywhere downstream (`CharacterSyncClient`, `DiscordRosterSync`, generic sync) to check "is a Discord account linked" and to authenticate against the bot.

**A single 401 must not unlink the account.** For a long time the most-reported problem with the app was that Discord had to be reconnected over and over. The cause was on the other side — the bot's pairing token was a key into a database its host wipes on every deploy, so a redeploy invalidated every link at once (fixed there with a signed, self-describing token; see `services/companion_token.py` in the bot repo). The *effect*, though, was produced here: five clients answered a 401 by calling `account_store.clear()` immediately, and to the user that is indistinguishable from having been thrown out. A 401 is not proof — it can be a bot that is restarting, a proxy in between, or a server-side failure dressed up as "token invalid". `DiscordAccountStore.note_auth_rejected()` is therefore the one place that decides, and it unlinks only after `AUTH_REJECTIONS_BEFORE_UNLINK` rejections inside `AUTH_REJECTION_WINDOW`. Two details: the counter lives **on the class**, because each client builds its own store while all of them answer the same one question ("does the bot still know this token") and a per-instance counter would need the threshold reached five times over; and `clear()` resets it, or a freshly re-linked account would inherit the old one's rejections and be gone again on its first hiccup. Isolated 401s days apart are two accidents, not a pattern — hence the window rather than a bare count.

### "What's new" popup

`gui/dialogs/whats_new_dialog.py`'s `show_whats_new_if_needed()` is triggered once via `QTimer.singleShot(0, ...)` at the end of `MainWindow.__init__` (independent of `CompanionManager`'s async init, since its content is local/bundled, not network-fetched). It compares `config.data["onboarding_seen_version"]` against `core.version.VERSION`: empty (fresh install or an upgrade from any pre-1.0 version, since the key never existed before) shows the hardcoded multi-page `TOUR_PAGES` feature walkthrough; any other mismatch shows the changelog entries between the two versions, read from the bundled `CHANGELOG.md` via `core/changelog_reader.py` (must stay listed in `WeintCompanion.spec`'s `datas`). Either way the dialog updates `onboarding_seen_version` on close; its "don't show again" checkbox sets `config.data["whats_new_enabled"] = False`, which short-circuits the whole check on future starts. Both are user-reversible via the "Willkommens-Tour" toggle/button in Settings → Allgemein (`gui/pages/settings_sections/general.py`), which calls `show_tour()` unconditionally (bypassing the seen-version check).
